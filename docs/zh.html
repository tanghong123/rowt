rowt1 / 25
为什么需要它

两条隧道，一张路由表。

你想让 Google 走自己的 VLESS 服务器，内网走公司 VPN，百度直连——而且是同时。

做不到。Shadowrocket 和公司 VPN 客户端都是数据包隧道：各自建一块 utun 虚拟网卡，各自想抢默认路由。macOS 只会让其中一个赢。

于是日常就变成了手动切换：连上公司 VPN，Google 没了；开个人 VPN，内网又进不去。来回折腾。

冲突在哪

两块 utun，一张路由表。后连上的那个拿走默认路由， 另一个就这么无声无息地失效了。

你真正想要的

按每条连接决定，而不是按整台机器。 google.com 走一条路，jira.corp 走另一条，baidu.com 再走第三条。

rowt2 / 25
它是什么

不是隧道，是代理。

rowt 把 sing-box 当成一个普通的用户态代理跑在 127.0.0.1:7890。代理不动路由表，自然也就没法跟公司 VPN 客户端打架。 应用把连接交给它，它来决定这条连接从哪出去。

常见 VPN 客户端rowt
实现方式数据包隧道（utun）监听端口的本地代理
路由表抢占默认路由只读不写
能否与公司 VPN 共存不能，只能活一个能，天然如此
分流粒度全量，或者你说了不算的分流按连接、按域名
是否需要 root需要不需要
判断依据目标 IP嗅探到的域名，在 DNS 之前

代价也说清楚：它只能管住愿意走代理的流量。裸 ping、ssh， 以及任何无视系统代理设置的程序，都会绕过它——这是设计如此，也写在文档里，不藏着。

rowt3 / 25
它是什么

四条通道。

escape

自己的隧道

VLESS / VMess / AnyTLS / hysteria2 连到你自己的 VPS。这条 socket 绑定在物理网卡上，所以哪怕公司 VPN 占着默认路由，它照样从家里的路由器出去。

google.com · youtube.com · geosite:github

corp

进公司 VPN

不绑网卡、交给系统解析器的 socket——于是它顺着系统路由表 径直进入 utunN。这条通道会自己长，见后面的 corp sync。

*.intranet.example.com · 10.0.0.0/8

direct

直接出去

绑定物理网卡，两条隧道都不走。没列进任何名单的流量默认走这里—— 国内站点保持原速，不绕路。

baidu.com · mirrors.debian.org · 其余全部

block

黑洞

当场拒绝——不解析、不连接。广告和遥测域名死掉之后会疯狂重试， 那点 CPU 就是这么被吃掉的，这条通道专治这个。

doubleclick.net · google-analytics.com

工作原理

命中即止。

一条连接进来，sing-box 先嗅探出目标域名——在任何 DNS 查询之前——然后自上而下逐条匹配。

# route.rules，按顺序 sniff domain 精确域名 → --domain 条目 domain_suffix 最长后缀优先 → 三个通道文件 rule_set geosite:… → 整个服务 ip_cidr 公司网段 → corp sync 同步来的 ip_cidr 私有/CGNAT → 组网对端 rule_set ads → 大而全的广告名单 final direct

最长后缀跨通道生效：escape 里写了 api.foo.com，就一定压过 block 里的 foo.com——谁先谁后不由通道顺序决定。

为什么看域名而不是 IP

CDN 的 IP 说明不了任何问题——同一个地址既服务被墙的站点，也服务正常的站点。域名才是目的地的身份，而嗅探拿到它的时机，早于任何解析器有机会污染它。

随时可以问它

rowt explain www.google.com www.google.com → ESCAPE matched: longest-match escape suffix 'google.com'

它复刻的就是真实规则；路由器在跑的话，还会顺手做一次真实 HTTP 探测。

rowt6 / 25
工作原理

三个层面，rowt 只管两个。

层面回答什么问题归谁管
通道走代理的连接从哪个出口出去rowt
DNS哪个解析器来回答这个域名rowt
系统路由不走代理的流量从哪块网卡出去刻意不管

DNS 跟着通道走

  • corp 域名 → 交给系统解析器，才能拿到内网地址
  • escape 域名 → 在 VPS 那一侧解析，出口看到的和你看到的一致
  • 其余 → 走物理网卡上的 DoH

为什么第三层不碰

改路由表需要一个常驻的 root 守护进程，而 root 进程绝不该去执行用户可写的代码。 rowt 是 brew 装的、用户可写、还经常更新——正好是最不该拿 root 的那种形态。它读这张表， 但从不写。

上手

让终端也用上它。

macOS 的系统代理只管得住浏览器和图形应用。命令行工具根本不看它，只认 http_proxy / https_proxy / all_proxy。 rowt 给了三种办法把这道坎填上。

按 shell
rowt-proxy-on rowt-proxy-off

在当前这个 shell 里设上、清掉这几个变量。 来自 rowt shell-init，顺带还装了 Tab 补全。

按命令
rowt run claude rowt run git pull

当场探测哪条路真的通得了外网—— 你 shell 里的设置、系统代理、rowt 自己的端口、直连——用第一条通的去跑命令。 一条都不通就直接不跑。

看一眼
rowt proxy status rowt proxy env

系统代理现在指向哪、是不是指着 rowt， 以及可以直接贴到别处去的那几行 export。

rowt run 存在的理由：机器上摆着好几个代理软件， 网络一天换好几次，"正确的值"一直在变。猜错了报的错还特别难懂——所以干脆别猜，测一下。

自动运转

不用你操心的那些。

只有 watch 需要装一次，其余默认就开着。

corp sync

读系统路由表，把公司 VPN 当前的网段镜像进 corp 通道， 让走代理的流量也能跟着进隧道。看门狗每一拍都会重跑——大约两分钟一次， 外加每次网络变化——所以 VPN 重连换了网段它也跟得上。手工加的条目它从不碰。

watch

一个 LaunchAgent：网络一变就重载；定时探测隧道，卡住或崩了会自动救回来； 登录时清掉残留的系统代理设置，免得 rowt 的影响活得比重启还久。

强制门户

酒店和机场的 Wi-Fi 登录页，一开代理就打不开。rowt 认得出这种网络， 先把代理摘掉让登录页能加载，等你过了再自动装回去。

geosite

一条命令加一整个维护好的服务—— rowt escape add geosite:google——不用自己去列后缀。更精确的条目永远压过它。

流量记录

collector 按域名把字节数写进分层存储，5 秒一格一直汇总到一年； 命令行可查，面板里翻一下也能看。

审计

每一次改状态的操作都记账，写清是你还是看门狗干的—— 连卡住没跑完的命令也有记录，因为 BEGIN 是动手之前就写下的。

进阶

三种模式，对付三种处境。

host

最常用的那种

sing-box 跑在 Mac 上，escape 的 socket 绑在物理网卡。 只要公司 VPN 客户端放行绑定网卡的连接，它就能用。

vm

绑不出去的时候

有些公司客户端是靠包过滤拦的，光绑网卡不够。 这时把隧道搬进一台桥接的 Lima 虚拟机，它有自己的局域网地址——在过滤器看来就是另一台机器。

local

人已经在墙外

干脆不建隧道。escape 通道的规则改指向 direct 而不是消失， 所以它仍然压得过范围更大的 block 条目。这种模式下连服务器都不需要。

怎么选

rowt up # 自动判断 rowt up vm # 强制指定 rowt probe # 这儿到底哪种能用？

不带参数的 rowt up 会自己探：在公司 VPN 开着的情况下，试试绑定网卡的连接能不能出去， 据此决定。它还会从物理网卡上探一遍 GFW 探针域名——如果都通，说明你人已经在墙外，那就选 local。

连着公司 VPN 时判断最准，所以切完网络记得再跑一次。

rowt22 / 25
底层

凭什么敢把流量交给它。

rowt 最早是一个很大的 shell 脚本。现在正在渐进式迁到 Rust， 而新旧两版之间靠一套差分测试台盯着，不是靠"应该没问题"。

每条命令都在一个碰不到真实机器的沙箱里、用两套实现各跑一遍， 比对四样东西：标准输出、退出码、整棵配置目录、以及每一个副作用命令的调用轨迹。

命令行界面 292/292 一致 通道编辑 28/28 渲染矩阵 23/23 规范化 JSON 分流判定 10/10 通道和理由都要对

这么做换来了什么

  • 一次不会悄悄改掉行为的重写
  • 顺手在老实现里翻出了 bug——测试台真的抓到过 shell 藏了好几个月的路由错误
  • 影子模式：两套实现同时跑，把分歧记下来，在真机上跑够时间，再谈切换

同一种克制也长在产品里：范围大到能匹配整个顶级域的条目会被拒绝， 待确认的改动会自己过期，每一次改动都可撤销、都有记录。
