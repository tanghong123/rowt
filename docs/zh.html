为什么需要它

两条隧道，一张路由表

这是一个资源独占问题，不是配置问题。

目标

Google 走自己的 VLESS 服务器，内网走公司 VPN，百度直连，三者同时成立。

障碍

Shadowrocket 与公司 VPN 客户端都属于数据包隧道，各自建立一块 utun 虚拟网卡，也都要占据默认路由；macOS 只让其中一个生效。

结果

反复手动切换：连公司 VPN，Google 不通；开个人 VPN，内网进不去。

冲突在哪

两块 utun 争同一张路由表。后连接的一方取走默认路由， 先连接的那个随即失效，且没有任何提示。

真正需要的

决定权在每条连接，而不是整台机器。 google.com 一条路，jira.corp 另一条，baidu.com 第三条。

它是什么

不是隧道，是代理

rowt 用 sing-box 起一个用户态代理，监听 127.0.0.1:7890。代理不碰路由表，自然不与公司 VPN 争抢资源； 应用把连接交过来，由它逐条判断该走哪个出口。

换一个层次解决问题：不在网络层抢路由，而在应用层做分发。

常见 VPN 客户端rowt
实现方式数据包隧道（utun）监听端口的本地代理
路由表占据默认路由只读，不写
与公司 VPN 共存不能，只能活一个可以，天然如此
分流粒度全量，或不可控的分流按连接、按域名
是否需要 root需要不需要

代价：只覆盖走代理的流量；裸 ping、ssh 以及任何不读系统代理设置的程序都会绕过。取舍写在明处，不做隐性承诺。

它是什么

四条通道，各行其道

escape

自己的隧道

连到自己的 VPS，支持 VLESS / VMess / AnyTLS / hysteria2。 socket 绑定物理网卡，公司 VPN 占着默认路由也不影响，照样经家庭路由器出网。

google.com · youtube.com · geosite:github

corp

进公司 VPN

socket 不绑网卡，域名交系统解析器处理，顺着系统路由表 直接进入 utunN。内容可自行生成，见后文 corp sync。

*.intranet.example.com · 10.0.0.0/8

direct

直接出网

绑定物理网卡，两条隧道都不走。未被任何名单命中的流量默认走这里， 国内站点保持原速，不额外绕行。

baidu.com · mirrors.debian.org · 其余全部

block

黑洞

当场拒绝，不解析也不连接。广告与遥测域名连不上会持续重试， CPU 往往因此被耗掉；这条通道正是为此而设。

doubleclick.net · google-analytics.com

工作原理

通道选择逻辑

自上而下，命中即止。

连接进来，sing-box 先嗅探目标域名，这一步早于任何 DNS 查询；取得域名后，逐条匹配规则。

# route.rules，按顺序 sniff domain 精确域名 → --domain 条目 domain_suffix 最长后缀优先 → 三个通道文件 rule_set geosite:… → 整个服务 ip_cidr 公司网段 → corp sync 同步 ip_cidr 私有 / CGNAT → 组网对端 rule_set ads → 广告规则集 final direct

最长后缀跨通道比较。escape 中的 api.foo.com 一定优先于 block 中的 foo.com，与通道先后无关。

为什么看域名，不看 IP

同一个 CDN 地址背后，既有被封锁的站点，也有正常的站点，IP 说明不了问题。 能标识目的地的只有域名；嗅探取得域名时 DNS 尚未查询，污染也就无从发生。

随时可以问

rowt explain www.google.com www.google.com → ESCAPE matched: longest-match escape suffix 'google.com'

复现的就是线上那套规则；路由器在运行时，还会补一次真实请求验证。

工作原理

职责边界

三个层面，rowt 只管两个。

层面回答的问题归属
通道走代理的连接从哪个出口出去rowt
DNS哪个解析器回答这个域名rowt
系统路由不走代理的流量从哪块网卡出去刻意不管

DNS 随通道而定

  • corp 域名交系统解析器，以取得内网地址
  • escape 域名在 VPS 侧解析，出口所见与本机一致
  • 其余走物理网卡上的 DoH

为何不碰第三层

改路由表需要常驻的 root 守护进程，而 root 进程不应执行用户可写的代码。 rowt 由 brew 安装、文件用户可写、更新频繁，恰属最不适合以 root 运行的一类。 按最小权限原则，这一层被主动排除在外：只读这张表，从不写入。

真正需要动路由表的场景，交给一个独立的小型守护进程， 与 rowt 不共享任何文件。

全程开着现有 VPN 操作，rowt up 需要联网下载 sing-box；整套跑通后再切回公司 VPN。这张清单可随时用 rowt onboard 打印，并标出当前进度。

05

切网络并验证

退出原 VPN，连接公司 VPN，各取一个域名确认走向。

06

通道配置

escape 出厂已带一份（Google、GitHub、维基、X 等）；corp 会从 VPN 路由自行生成。按需补充：

rowt escape add youtube.com googlevideo.com rowt escape add geosite:google # 一整个服务 rowt corp add '*.intranet.example.com' 10.0.0.0/8 rowt block add ads.example.com

geosite:<名称> 引入一份维护好的规则集，涵盖该服务的全部域名与各国后缀，无需逐条罗列；更精确的条目仍然优先。

rowt corp suggest # 依据 DHCP 搜索域推断 rowt corp sync # 连着公司 VPN 时执行，同步其路由

连接状态下执行一次 corp sync；此后看门狗每一拍自动重跑。

上手

命令行代理配置

系统代理只覆盖浏览器与图形应用。命令行工具不读系统代理，只认 http_proxy / https_proxy / all_proxy。rowt 提供三种方式。

按 shell
eval "$(rowt shell-init)" # 写入 ~/.zshrc，一次即可 rowt-proxy-on rowt-proxy-off

这两条别名由 rowt shell-init 提供， 在当前 shell 内设置与清除上述变量；同时装好 Tab 补全。

按命令
rowt run claude rowt run git pull

当场探测哪条路径确实通得了外网：当前 shell 的设置、系统代理、 rowt 自身端口、直连，取第一条可用的执行命令；全部不通则不执行。

查看
rowt proxy status rowt proxy env

系统代理当前指向何处、是否指向 rowt， 以及可直接粘贴到别处的 export 行。

rowt run 的由来：机器上并存多个代理软件， 网络一天多变，"该填哪个值"始终在动；猜错后的报错又难以定位。与其猜，不如现测。

自动运转

智能路由，自动运转

仅 watch 需安装一次，其余默认启用。

corp sync

读取系统路由表，把公司 VPN 当前的网段镜像进 corp 通道， 使走代理的流量同样能进入隧道。看门狗每一拍重跑一次，约两分钟一轮，网络变化亦会触发； VPN 重连后换了网段也跟得上。手工添加的条目不受影响。

watch

一个 LaunchAgent：网络变化即重载；定时探活隧道，卡死或崩溃可自动恢复； 登录时清理残留的系统代理设置，避免 rowt 的影响跨越重启。

强制门户

酒店与机场的 Wi-Fi 登录页在开启代理时无法打开。rowt 能识别此类网络， 先摘掉代理让登录页加载，认证完成后自动恢复。

geosite

一条命令接入整个维护好的服务： rowt escape add geosite:google，无需自行罗列后缀；更精确的条目仍然优先。

流量记录

collector 按域名写入分层存储，5 秒一格逐级汇总至一年； 命令行可查询，面板中切换视图亦可查看。

审计

每次状态变更均记账，并标明由本人还是看门狗发起； BEGIN 在动作之前写入，因此卡死未完成的命令同样留痕。

进阶

三种运行模式

对应三种处境。

host

最常用

sing-box 运行在 Mac 上，escape 的 socket 绑定物理网卡。 只要公司 VPN 客户端放行绑定网卡的连接即可使用。

vm

如果绑定网卡不生效

部分公司客户端以包过滤拦截，仅绑定网卡不足以绕开。 此时把隧道移入一台桥接的 Lima 虚拟机，它拥有独立的局域网地址，在过滤器看来即另一台主机。

local

人已在墙外

不建隧道。escape 通道的规则不会消失，而是改指向 direct， 因而仍然优先于范围更大的 block 条目。此模式无需配置服务器。

如何选择

rowt up # 自动判断 rowt up vm # 强制指定 rowt probe # 当前环境适用哪种

不带参数的 rowt up 会自行探测：在公司 VPN 开启的前提下，验证绑定网卡的连接 能否出网，据此决定模式；同时从物理网卡试探若干探针域名，若均可达，说明当前已在墙外， 直接选用 local。

连接公司 VPN 时判断最准，切换网络后建议重跑一次。

工程

工程保障

凭什么把流量交给它。

rowt 最初是一个庞大的 shell 脚本，目前正逐块迁移到 Rust。 新旧两套实现之间由一套差分测试台把关，而不是靠"应该没问题"。

每条命令都放进一个接触不到真实机器的沙箱，用两套实现各跑一遍，比对四项产物： 标准输出、退出码、整棵配置目录、以及每一个副作用命令的调用轨迹。

这样做换来什么

  • 重写过程不会悄悄改变行为
  • 顺带在旧实现中查出缺陷：测试台确实抓到过潜伏数月的分流错误
  • 影子模式：两套实现同时运行，记录分歧，在真机上跑满观察期后再谈切换

同一种克制也体现在产品里：范围大到能匹配整个顶级域的条目会被拒绝， 待确认的改动会自动过期，每次改动均可撤销、均有记录。
